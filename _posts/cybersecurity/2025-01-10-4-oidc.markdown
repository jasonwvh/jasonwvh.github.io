## OpenID Connect Simplified

We established that OAuth 2.0 is a framework for *delegated authorization*, but explicitly not for *authentication*. Relying on an Access Token to log a user in is a common anti-pattern.

This is the exact problem **OpenID Connect (OIDC)** was created to solve. Published in 2014, OIDC is a thin identity layer built directly on top of OAuth 2.0. It provides a standard, secure, and API-friendly way to perform authentication.

### The Missing Piece: The ID Token as a JWT

OIDC's central innovation is the **ID Token**. While an OAuth Access Token is an opaque string meant for a Resource Server, an ID Token is a structured data format meant for the Client application. It is a **JSON Web Token (JWT)** that provides verifiable claims about the authentication event and the user.

A JWT consists of three parts, separated by dots (`.`):
1.  **Header:** A JSON object declaring the token type (`JWT`) and the signing algorithm (e.g., `RS256`), which is then Base64Url-encoded.
2.  **Payload:** A JSON object containing the "claims" about the user and the authentication event. This is also Base64Url-encoded.
3.  **Signature:** A cryptographic signature created by signing the encoded header and payload with the private key of the Authorization Server (now called an OpenID Provider or OP).

The Client can validate the signature using the OP's public key, proving the token's authenticity and integrity.

### Core OIDC Claims

The ID Token payload contains standard claims, including:
*   `iss`: The **Issuer** identifier of the OP.
*   `sub`: The **Subject** identifier, a unique and stable ID for the user at the given issuer.
*   `aud`: The **Audience**, which must contain the Client's `client_id`. This prevents a token issued for one client from being used at another.
*   `exp`: The **Expiration time** after which the token must not be accepted.
*   `iat`: The **Issued At** time.
*   `auth_time`: The time the user's authentication occurred.
*   `nonce`: A string value used to associate a Client session with an ID Token and to mitigate replay attacks.

### The OIDC Authorization Code Flow

The OIDC flow is a deliberate extension of the OAuth 2.0 flow.

1.  **Authorization Request:** The flow starts like OAuth 2.0, but with two crucial changes:
    *   The `scope` parameter **must** include `openid`. This is the trigger that tells the Authorization Server to perform an OIDC flow.
    *   A `nonce` parameter, a unique and unpredictable string generated by the client, **should** be included to prevent replay attacks.
    *   A `state` parameter, a unique string to maintain state between the request and callback, **must** be included to prevent Cross-Site Request Forgery (CSRF).

    ```
    https://op.example.com/authorize?
    response_type=code&
    client_id=CLIENT_ID&
    redirect_uri=https://client.com/callback&
    scope=openid%20profile%20email&
    state=af0ifjsldkj&
    nonce=RANDOM_STRING
    ```

2.  **Token Exchange:** After the user authenticates and the client receives the authorization code, it exchanges it at the token endpoint. Because the original request included the `openid` scope, the response now contains an `id_token` alongside the `access_token`.

3.  **ID Token Validation and Login:** The Client receives the ID Token. Before it can trust the token and log the user in, it **must** perform these critical validation steps:
    *   Verify the JWT signature using the OP's public key (which it can discover from the OP's `.well-known/openid-configuration` endpoint).
    *   Validate the `iss`, `aud`, and `exp` claims.
    *   Verify that the `nonce` in the ID Token payload matches the `nonce` it sent in the initial request.
    *   Verify that the `state` parameter returned with the authorization code matches the one it sent.

    Only after all these checks pass can the client establish a session for the user.

### Other Flows and Endpoints

*   **Hybrid Flow:** OIDC also defines a "hybrid flow" (`response_type=code id_token`) where the ID Token is returned directly from the authorization endpoint (like the Implicit flow) alongside an authorization code. This allows the client's frontend to quickly inspect the token and validate the user's identity, while the backend can securely exchange the code for an access token.
*   **UserInfo Endpoint:** OIDC standardizes a `/userinfo` endpoint. The client can present the `access_token` to this endpoint to retrieve the latest user profile claims (like `name`, `email`, `picture`), which are not part of the ID Token's authentication-related data.

### Conclusion: The Modern Standard for Authentication

OIDC successfully adds a missing identity layer on top of OAuth 2.0, creating a complete, modern, and API-friendly protocol for both authentication and authorization. It has become the de facto standard for consumer-facing and enterprise login, powering "Sign in with..." buttons across the web.
